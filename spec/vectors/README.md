# Pubky Dispatch test vectors

Test vectors for the Pubky Dispatch's wire format in `spec/wire-format.md`. Every file is computed from fixed
keys and fixed randomness, by the reference prototype's own code, shared separately, or, for the cases
"How the files were generated" lists, by `pubky-dispatch-core`, so any implementation of the Dispatch, a signer
or an app can check its encodings, signatures, derivations, envelopes and state rules against them byte for
byte.

The files use a sample protocol, `tasks`, described in the spec's Section 1, whose names the Dispatch treats as opaque: the scopes, message kinds, collections and app record member in them are those of `tasks`. This set depends on no other.

### HTTP cases

[http.json](http.json) covers signed requests from each caller kind, the service's signed responses, requests received differently from how the caller sent them, and a push webhook. In `responses`, `request` names the request case, or is `null` for an unsigned public read. The response signature covers its status, the request **as received** (`received_request`), the service time, the head field and the body (wire 7.1).

- **Enrollment and erasure (wire 3.7, 7.4.16).** The request cases cover enrollment and the account's first `identity.json` delivery. The enrollment answer gives `limits.max_import_bytes` and the account's creation time in `created`. Each erasure request names that creation time. The request before the first delivery and the one naming the held identity return `{"erased":true}`. The mismatched identity returns `409 conflict` with `current.created`. Enrollment and erasure answers have no head.
- **Directory, feed and operations (wire 7.1, 7.4).** Bob's shop reads alice's directory with its certificate and receives `known_version`. The same caller's append can return `409 stale_key` or `429 rate_limited`, both without `known_version`. The wallet's ordinary feed page follows `1:4`. Its long poll has a case with two invitations from the same peer and an ordinary follow-up. The `POST /ops` answer proves the batch at `seq` 7 and 8.
- **Peer admission (wire 7.4.3, 7.4.6).** Alice's wallet reads `/allow` in the long-poll example with three inbox entries after the signed head at 41. Before that head, bob needed a different single-use invitation to enter. He redeemed the first 16 bytes of seed `admission/original-code` at 00:04:58.050 UTC on January 1, 2026. The service created his reply grant, and alice's wallet then kept him. The wallet granted the identity in `claims.json` a reply at 00:04:59.165 UTC. That peer has sent nothing since. The wallet also kept carol, whose Ed25519 seed is the BLAKE3 hash of the UTF-8 string `pubky-dispatch/test/carol/identity`. Her seed is built from the namespace alone (the text of `labels::PREFIX` before its first `/`, followed by `/test/`), where every other seed is built from the seed prefix: a change of the project name moves it with the rest, a change of the seed prefix alone does not. Alice registered the two single-use invitations for entries 42 and 43 before head 41. Those entries use up the two codes. Bob's ordinary append at 44 sets his grant's last use to 00:05:00.150 UTC and preserves the earlier code hash. The wallet signs its read at 00:05:00 UTC and the service answers at 00:05:00.250 UTC with the same chain head. The three peer rows are in encoded Pubky ID order. The deny, flagged and live invitation lists are empty. The frozen export in `export.json` follows a separate history that freezes at head 10.
- **Peer admission after a wallet change (wire 6.2, 6.5, 7.4.6 and 10.3).** The same signed read has a second answer from a separate history. The `peer_admission` sequence in `chain.json` starts at head 9. Bob's first delivery creates his reply grant, and the wallet then keeps him. - **Public identity reads (wire 7.3).** The three unsigned requests are `GET`s. The service signs all three responses without a head. The two successful reads include `Cache-Control: public, max-age=60, must-revalidate`. The frozen account's response includes the freeze from `documents.json`. Alice's service answers the read for bob, whom it doesn't host, with `404 not_found` and `current` set to `{"hosted":false}`.
- **Identity changes (wire 3.12, 7.4.2, 7.4.5).** Omitting generation 1's service key at generation 2 gives `409 conflict` with `current.proof_generations` set to `[1]`. The new signer's version 4 names its own install as `signer`. After the old signer's version 5 abort wins, the take-over delivery gives `409 stale_identity` naming version 5. Both refusals have a head.
- **Peer identity deliveries (wire 7.4.5).** Alice's wallet signs both deliveries of her version 3 for bob's origin. Bob's Dispatch already holds that version. It signs both responses with its service key, without a head. The same body is a no-op with `{"known_version":3,"version":3}`. - **Hand-over (wire 7.4.17).** Alice's signer stores the hand-over for her phone with `PUT /handover`. The reply gives the phone's `app_id` and `parts` set to 2. The phone signs `GET /handover` and receives the stored body. Both replies have a head.
- **Export transfer (wire 10).** The next service signs its chunk fetch under `pubky-dispatch/v1/transfer-request`. The old service signs the chunk response with its key, without a head.

#### Requests as received and the webhook

In `received_cases`, `request` names the original case and `received` records which body or headers the service received. The signature in each case verifies against `received_request`. In the first three, it fails against the request as sent. In the fourth, verification against the request as received still leaves a head the client must refuse (wire 7.1).

| Case in `received_cases` | What changes |
| --- | --- |
| `a 413 too_large given before the body is read, over the empty body field` | The service signs the empty body field before reading the request body. |
| `a signed request header present with an empty value, 400 bad_request` | `Dispatch-Invite-Code` is present with an empty value. |
| `a signed request header sent twice, 400 bad_request` | `Dispatch-Timestamp` is present twice. |
| `an answer with a present, empty Dispatch-Head, which no client takes` | The head field hashes the empty header text. The client refuses the response. |

The separate `webhook` case includes the relay URL, relay origin, body, headers and service key for a push delivery (wire 8.2).

## Conventions
- **Seeds.** Every fixed secret and random value is `BLAKE3("pubky-dispatch/v1/test-vectors/" + label)`, the prefix also quoted in the description of `keys.json`, cut to the length needed (16 or 24 bytes take the first bytes). Labels appear in the files where they help, for example `alice/identity` or `alice/wallet/receive/0`. X25519 secrets are clamped (RFC 7748) after that. UUIDs are UUID v4 built from the first 16 bytes of a seed.
- **Encodings.** `*_hex` fields are lower-case hex; other binary values are base64url without padding, as on the wire. JSON that is signed or hashed appears as a string holding its exact bytes (`body`, `json`, `envelope_json`); parse it, but compare and hash the string's bytes.
- **Times.** Static vectors start at `2026-01-01T00:00:00.000Z`. `claims.json` runs on a test clock starting at its `start_time`.
- **Sections.** Descriptions and the table above cite sections of `spec/wire-format.md` as "wire N"; "spec N" is the Pubky Dispatch spec.
- **HPKE randomness.** An envelope fixes, per recipient, the 32 bytes of keying material `ikmE` from which HPKE derives its ephemeral key (RFC 9180 `DeriveKeyPair`). An implementation whose HPKE library can't take `ikmE` can take `sk_e_hex` instead, or check only that it opens every envelope to the given plaintext.
- **Scope keys and blinding.** Scope keys and naming keys are derived from each identity's Dispatch root (wire 1.5); `keys.json` lists them, and `sealed.json` and the key bundle use them. Record keys are blinded with the naming key of the identity whose Dispatch holds them: alice's for her `task_items`, `task_lists`, `shares` and `share_runs` records, bob's for his `task_assignments` records. Claim keys are opaque to the service (spec 10.2): the files hold them as inputs, and their derivation belongs to the protocol that uses claims.
- **Record versions** are the (generation, `seq`) of the write that produced them (wire 6.2): `operations.json` and `chain.json` follow one record from its create at `seq` 6 to its delete, each write naming the version it read in `expected_version`. After `chain.json`'s revoke at `seq` 9, the done batch (`claim done (owner)` and `record.put after done`) takes `seq`s 10 and 11, so the delete names (1, 11).
- **Claims.** Each `write` step sends one batch with one claim operation, built from the step's `entry` and published in `op`. Its `expect` is `GET /claims/{claim_key}` as app A sees it after the write, or the error's status, code and `current`. Owners and attempts are named in `apps` (with their Dispatch permissions and the seed label of the signing key their App ID comes from) and `attempts`.
- **Export.** Service keys are fixed only in these vectors; a real service makes its own. `export.json` is alice's account frozen right after `chain.json`'s last item: its chain ends at the freeze transition (`seq` 10), while `operations.json` continues the account past `seq` 9 instead. It is a complete export, which a next service enrolled with alice's version 3, at the freeze's time, activates; the reference prototype tests this. Only the wallet registers in that chain, so the phone's and the executor's `app` parts hold no record or receive key; the inbox entry at `seq` 5 isn't exported, since the wallet moved its cursor past it. A record's `size` is its `ct` decoded (wire 9.1). Completing it changed `export.json`, and, through the manifest hash, the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`; nothing else.
- **First document:** alice enrolled without a document, so her account's first `identity.json` is version 1 at generation 1 and data epoch 1 (wire 3.3): `http.json`'s delivery and `chain.json` seq 1. Her version 3, at data epoch 2, follows at seq 2; versions need only increase. The generator replays the enrollment and that delivery on the prototype service, which chains it as seq 1 and refuses version 3 as a first document.
- **Erasure** (wire 7.4.16). `http.json`'s erasures are the core's (How the files were generated), each naming the account's creation time, the `created` of the enrollment answer. The service replays the first at alice's account after that enrollment and before her first delivery, which holds no `identity.json`, so it names none: it gets exactly the vector's answer body, without a head, and a repeat is the signed not-hosted `404` (wire 7.3 step 2). The two that also name an `identity.json` are replayed at her account holding version 3: their answers are what it signs with alice's service's fixed key, the `409 conflict` carrying in `current.created` the creation time it was checked against.
- **Certificate lifetimes** (wire 3.1). Every certificate expires, within 730 days of its `issued_at`. The fixture certificates are issued 31 days before the start time and expire 365 days after issue, except `phone`'s (one year after the start) and the renewed `wallet` certificate (90 days after the start).
- **Sealed value padding** (wire 6.2). Every sealed shared record value is `u32_be(len) || JSON || zeros`, padded to its size bucket, except a delete, which stays empty. Bringing in the padding changed every value built on a sealed value: the `ct` of each `record.put` in `operations.json`, `chain.json`, `http.json` and `export.json`, and the signatures, item hashes, chain hashes, stubs, proofs, heads, chunk and manifest built on them; checked against the files before the change, nothing else differs.
- **Key bundle certificates** (wire 3.5). Every key bundle part names, in `cert`, the document hash of the certificate it was made for: `envelopes.json` `key_bundle` names the executor's certificate and `documents.json` `approval` the wallet's. The parts' envelopes and signatures, the key-bundle case of `signatures.json` and `operations.json` `key_bundle.put` carry it.
- **Reconciliation window** (wire 6.8). A tombstone, and a claim whose every attempt failed, are kept until the service clock reaches the pinned deadline plus 30 days. In `claims.json` O7's tombstone is still there at its deadline (steps 41 and 42), and a 30-day advance at the end shows it deleted. O10 is a failed claim that a late receipt settles after its deadline.
- **No-op batches** (wire 6.4). `claims.json` `noop_batch` steps send an unchanged `app.put`, by app A conditioned on claim O11's step, and by the revoked app C: without `cursor.set` a failing condition is answered as a no-op; with it the condition is checked (`409`), a condition that holds moves the cursor with no proof, and C is refused at authentication (`403 not_current`). Each step gives the exact request body. `claims.json` gives the account (`identity`, from the seed label `identity_seed_label`) and per app its certificate and the app record and receive key record it registered (`apps`); its `identity.json` names a service key drawn at random, so only its contents are described.
- **Kept record proofs** (wire 7.4.9, 10.3). The service keeps the transition proof of a record's current write with the record, so `export.json`'s record part carries `chain.json`'s proof for `seq` 8. That changed the chunk, the manifest, and through the manifest hash the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`; nothing else.
- **Key retention conflict** (wire 7.4.2). The generator replays `http.json`'s key change on the prototype service, whose key is drawn at random, as a service key change in place (spec 12.5): an identity writes a record at generation 1, the service changes its key, the identity enrolls again for the new key and delivers a document naming it without generation 1's key, and the service's answer body is the vector's. It then checks the generations come ascending: kept at generation 2, a write there, and both left out at generation 3 give `[1, 2]`.
- **A reduction rotates** (wire 3.8). The `wallet` renewal drops `tasks_people_admin`, which has keys, so `documents.json`'s versions 4 and 5 carry `data_epoch` 3 where version 3 has 2; their `until` is the renewing delivery's time plus the tolerance.
- **Separate export parts** (wire 10.3). `export.json`'s live claim carries no entries: its one entry follows it as a `claim_entry` part, and the claim names its `creator` and `last_entry_ms`; `app` parts carry no key bundle parts (none are stored in this chain). That changed the chunk, the manifest, and through the manifest hash the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`.
- **Claim entries' certificates** (wire 10.3, 10.5). A `claim_entry` part carries `cert`, the writer's certificate the entry was checked against, or `null` when the writer's `app` part carries it, as a record part does; `export.json`'s is `null`. That added `"cert":null` to the chunk, and changed the manifest and through the manifest hash the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`; nothing else. `claim_rejections` gained the two cases the replay of the entries and their writers' signatures refuse.
- **Reachable apps only** (wire 10.3). `export.json`'s meta part gives `app_added_at` for the reachable apps alone, as the service keeps it: the wallet, current with a receive key. The phone is revoked and the executor has no receive key, so neither has an entry. That changed the chunk, the manifest, and through the manifest hash the same documents, signatures and answers as above.
- **The version held again** (wire 7.4.5). bob's Dispatch, in `http.json`, holds alice's version 3. Its answers to her wallet's two deliveries of version 3 are built as the Dispatch builds them: the refusal of the other body by the Dispatch's own constructor, whose body the prototype's tests compare with the Dispatch's answer. The other body is her version 3 with connect requests on, signed with her key; the two bodies at one version are equivocation (wire 3.3).
- **The Dispatch's names** (wire 1.5, 2.3, 4.1, 7.1). The formats of the Pubky Dispatch sign and derive under `pubky-dispatch/v1/` labels, its headers are `Dispatch-*` (sent in lower case), its Homeserver paths lie under `/pub/pubky-dispatch/v1/` and, for the signer's backup and the apps' backups, `/priv/pubky-dispatch/v1/` and its envelopes start with `PDI1`; the Seeds rule above gives the prefix for the vector keys and randomness.
- **Signer IDs** (wire 3.3). Every `identity.json` names its signing install in `signer`: alice's documents `b64(seed alice/signer)`, bob's `b64(seed bob/signer)`, and the phone's take-over delivery in `http.json` `b64(seed alice/phone/signer)`.
- **Executor batch.** The executor batch in `operations.json` takes over the wallet's task after the wallet's attempt failed (`claim failed`): an `attempt` at step 2, before the deadline, and, in the same batch, a `share_runs` `record.put` under `tasks_share_run`, conditioned on the version of the `shares` record and on a server time window.
- **Attempt deadlines** (wire 6.2, spec 10.2). An attempt carries `d + 1 ms`, for a `d` its protocol computes, taken at millisecond precision. The wallet's attempt, whose `d` is `2026-01-02T00:00:00.000Z`, pins `2026-01-02T00:00:00.001Z`, and the executor's attempt names the same. That deadline is in the claim attempt of `operations.json` and in `chain.json` `seq` 7, so the chain hashes from `seq` 7 on, the proofs and heads built on them, `export.json`, the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the feed page, `POST /ops` answer and chunk of `http.json` carry it too.
- **Sub-scopes** (wire 1.5, 3.1). bob's `hosted` app holds only `tasks_assign:team1`; it comes after `keys.json`'s other apps and isn't in bob's `identity.json`. Its keys are the sub-scope keys of `tasks_assign:team1`, bob's `tasks_assign` keys derived once more (`sub_scope_keys`).
- **Permissions** (wire 3.1). A certificate's Dispatch permissions are its `permissions` member, signed with the rest; the Dispatch checks their form and enforces them as signed.
- **Protocols' members** (wire 3.2). An app record carries what its protocols add under `protocols`. The records of `documents.json`, all of apps of `tasks`, hold its member, `protocols.tasks`: the board kinds each app supports (`features.board_kinds`) and its public boards (`public_boards`), one for `shop`. The records registered in `claims.json` carry an empty `protocols`. The equal-time `app_put` adds a `tasks` member to one of those records so its signed body differs at the same timestamp. `documents.json` `app_record_protocols` checks the form of `protocols`. The member is part of every value built on an app record: the record's signature, the `app.put` operation, the chain items, proofs and heads that follow it, the export and the HTTP bodies that carry them.
- **Invitations** (wire 6.2, 7.4.3, 7.5, 10.3). The signed feed page after `1:4` carries JSON `null` for entry 5, accepted at 00:00:02 UTC. The signed append request at 00:05:01 UTC presents a code with that same envelope. A retained retry keeps the original entry. An alternate signed answer to the long-poll after `1:41` shows three assignments from bob's shop to alice's wallet. At the head at 41, alice has registered both single-use codes and bob already has admission. Entry 42 names the hash of the code in `identifiers.json`, entry 43 names the hash of the first 16 bytes of seed `invitations/second-code`, and entry 44 carries JSON `null`. For each entry use `invitations/<seq>/entry` for its 16-byte entry ID, `/message` for its message UUID and `/cek`, `/nonce` and `/ikm-e` for sealing to the wallet. The entries are accepted 50, 100 and 150 milliseconds into 00:05 UTC on January 1, 2026. The response carries the same head at 41 since inbox entries have no chain stubs. The separate `pending_entry` in `export.json` is the exact export part for entry 43 while it is pending.
- **Rejections.** Where a file lists inputs to refuse (the `rejections` of `chain.json`, `envelopes.json` and `signatures.json`, the refused case of `chain.json` `batch_id_window`, `documents.json` `permission_rejections` and the `refused` cases of `scope_rule`, `app_record_protocols` and `size_caps`, `envelopes.json` `key_bundle_rejections` and `signer_handover_rejections`, `export.json` `record_rejections` and `claim_rejections`, `operations.json` `unknown_members` and its `batch_entries` and `integer_bounds`, `shape_rejections` and the `rejections` of `permanent_policies`, `documents.json` `approval.rejections` and `identity_rejections`, the errors of `claims.json`), what is normative is that the input is refused, and the HTTP status and `code` where the wire document fixes one. An `error`, `message` or `reason` text is that of the implementation that generated the case, and only informative; an `error` or `reason` text is quoted without the section number it starts with there.

The wire 6.2 table requires `id_inputs` on every record write and its Derivation bullet derives both addresses on every write, but the core rejects `id_inputs` on updates and deletes, and the vectors follow the core.

One inherited example needs a later vector change because correcting it changes published values: the invitation URI names Bob, while Alice's wallet registers the code hash and the HTTP example presents the code to Alice.

## How the files were generated
A reference prototype, shared separately, generated every file but the cases `pubky-dispatch-core` adds (below). The core's vector tests read every file and check the published bytes and expected verdicts. The coverage table below identifies the values the core writes. The rebuild test checks which carriers it can reproduce with their published values blanked. The signer's, the client's and the service's tests check their own parts against the same files.

`pubky-dispatch-core`, the Dispatch's core crate in this repository, added these cases, each built from the fixed keys and the files' own values, with the seeds of this README where it seals:
- `export.json` `claim_rejections`: the `failed` entry signed by the executor under its own certificate, naming the wallet as its writer, and the claim marked `rebuilt` on an account without a provider loss;
- `documents.json` `approval.rejections` (the part through data epoch 3) and `identity_rejections` (the two `connect_requests` cases);
- `identifiers.json` covers the create and delete scope tags alone and together, with and without permanence (wire 1.5). `operations.json` `record_scopes` uses the wallet and executor grants to exercise create, update and delete authority. The nonce and batch ID use the seeds `operations/record-scopes/<name>/nonce` and `operations/record-scopes/<name>/batch` (wire 6.2).
- `documents.json` `size_caps` (the wallet's certificate and receive key record, each body padded with whitespace before its closing brace to `body_bytes` and signed again by its writer: at the cap accepted, one byte over it refused for size alone);
- `operations.json` `shape_rejections` (the record scopes that aren't scopes, each create's key derived again for its policy, the key bundle ranges out of the rule, and the rule of a permanent policy: `record.put delete` without its claim condition at a policy naming no generation, and `record.put create` at one naming another generation, each key derived again for its policy; each record case's value is sealed again for its own address and scope, with its base operation's nonce and value, so it opens where it is written and is refused for its shape only) and `permanent_policies` (the `record.put create` at a policy naming no generation and at one naming generation 1, each key derived again for its policy, its value sealed again for that key with the seed `operations/permanent/<g>/nonce`, `null` or `1`, under the batch ID of the seed `operations/permanent/<g>/batch`; and that second case with its `permanent` member written in each refused form);
- `operations.json` `deny_room` (wire 7.4.14): each case's answer computed by the core's deny room rule from its held entries and uploaded entries, the Pubky IDs those of 32 repeated bytes;
- `identifiers.json`: the permanent policies `task_closures, permanent`, naming no generation, and `share_counts, permanent for generation 1` (wire 1.5, 6.2), with a record key under each: `task_closures record of a task done without an assignment`, on that `task_items` record's natural key, and `share_counts record of generation 1`, on the natural key of `shares record` followed by `lp(u64(1))`;
- `chain.json` `record_delete` (the delete sealed with the seed `chain/record_delete/nonce`, in the batch of the seed `chain/record_delete/batch`);
- `envelopes.json` `signer_backup` (the records of `signer_handover` with `prev` as a backup's plaintext, sealed with the seed `envelopes/signer_backup`), with `signatures.json`'s case of the backup's label;
- `http.json`: the `cursor` of the feed pages (wire 7.4.4), 0 on alice's wallet's page after `1:4`, before its first cursor move, and 41 on the long-poll's page at `1:41`, each placed before the page's `head`; on alice's wallet's page, the record's create at `seq` 6 as its stub, `{"type":"stub","seq":6,"stub":...}`, since the attempt batch's write at `seq` 8 supersedes it (wire 7.5); and the answer signed again with her account's fixed service key, answering the page's own request at its server time, with `signatures.json`'s `pubky-dispatch/v1/http-response` case, which is the long-poll page's;
- `http.json`: the enrollment answer (wire 3.7), the answer to the file's enrollment with its service key and limits, naming in `created` the time it was answered at, when the account was created; and the three erasures (wire 7.4.16), each naming that creation time: alice's request at her account before its first delivery, naming no `identity.json`, and the one naming her version 3, each with its `{"erased":true}` answer, and the one naming her version 1 with its `409 conflict`, whose `current` carries `created`, each signed with her identity key at the erasures' timestamp, each answer with the service key at the erasure answers' time, without a head;
- `http.json`: the requests of the three responses the reference prototype wrote without theirs, signed with the fixed keys of `keys.json` at the second of each answer's time, each with the request signature that answer named: bob's shop reading alice's directory with its certificate (`GET /v1/{alice}/directory`, `2026-01-01T00:05:00Z`), alice's wallet reading her feed after `1:4` (`GET /v1/{alice}/feed?after=1:4&limit=100`, `2026-01-01T00:05:02Z`), and the wallet sending the batch of `chain.json` `seq` 7 and 8 (`POST /v1/{alice}/ops`, body `{"ops":[...]}` with the two operations as the chain holds them, `2026-01-01T00:00:03Z`); they come after every other request;
- `http.json`: in every response, `request`, the name of the request case it answers, `null` for the three unsigned public reads, and `received_request`, that request as the service received it (wire 7.1), field by field and its bytes: of the request case it names, its body read whole, or, for the public reads, an unsigned `GET` of `identity.json` with no header, at alice's account, and for the not-hosted `404` at bob's, whom that service doesn't host; and its signature over its status, the received request, its server time, its head field and its body, in `fields`, `signed_bytes_hex`, `signature` and `dispatch-service-signature`, with the fixed key of its `public_key`, and the same values of `signatures.json`'s response signature case; and the `404 not_found` itself, answered at the time base with `current` `{"hosted":false}` and signed with the service key that signs alice's answers. The `404`'s name says it is signed with the service key, without a head.
- `http.json` `received_cases`: four answers to a request case as the service received it otherwise than it was sent, each naming the case in `request`, how it was received in `received` (`"body": "not read"`, or `headers`, every header as received, a `[name, value]` pair in order), and that request as received in `received_request`, signed with alice's service key at the second the request was signed: a `413 too_large` given before the body is read, over the empty body field; a `400 bad_request` for `Dispatch-Invite-Code` present with an empty value, and for `Dispatch-Timestamp` sent twice (wire 7.1 "Each header once, as text"); and an answer that carries a present, empty `Dispatch-Head`, whose head field is `BLAKE3` of the empty text, which a client fails (wire 7.1). Each verifies for the request as received and, but the last, not for the request case as sent.

Its vector tests build each of these cases again and compare it with the file, value for value, and check that it is refused, or taken, by the rule it names; the generator lives in the crate's tests, with the fixed sealing randomness of its test-only `test-vectors` feature, which no production build enables. The tagged permanent policy hash also changed the corresponding policy and record bytes in `identifiers.json` and signed bodies in `operations.json`. Earlier additions include new members in `documents.json`, `operations.json` and `chain.json`, new entries of `claim_rejections` in `export.json`, in `http.json` the enrollment answer's body, the first erasure request and its answer, and the not-hosted `404`'s key, body and name in their places, five requests and two responses after the others, the four new `received_cases`, and in every response the members its signature decides, with `request` and `received_request` new, and in `envelopes.json` the whole `signer_backup` member, with the backup label's case in `signatures.json`. The feed pages' `cursor` and the stub at `seq` 6 changed only those two pages: each body, its `BLAKE3(body)` field, the signed bytes and the response signature, in the answer and its `dispatch-service-signature` header, and the same values of `signatures.json`'s response signature case.

After an intended wire change, run the core's writer, verify the published files with the ordinary vector tests, and read the diff.

```sh
PUBKY_DISPATCH_WRITE_VECTORS=1 cargo test -p pubky-dispatch-core --test vectors -- --ignored --exact generation::regenerate_vectors
cargo test -p pubky-dispatch-core --test vectors
```

The writer stages all twelve files in memory. The identifier producer takes keys, message inputs and policy choices from the fixtures. HTTP signs the issued documents, chain and export data and the hand-over. The operations producer takes the registration, first attempt, record writes and proof from the chain. It uses the issued certificates, the incremental key bundle, the invitation and the share record addresses from their producers in memory. Signatures are checked against the staged carriers. Both writer modes check coverage on all twelve staged files before comparing or publishing any file.

It checks that the producers emit exactly those leaves and reproduce their published values.

The operations description uses the operation signature label. The chain description uses the item and chain hash labels. The export description uses the manifest signature label and the service key's seed label.

**Seed labels held beside the values they make**

- `keys.json` supplies the identity, app and service key seeds. The removed app's `signing_seed_label` determines its App ID.
- `identifiers.json` uses `invite_code.code_seed_label` for the 16-byte code, its hash and its link to the named account. The unassigned task uses `attempt_seed_label`, the share uses `share_seed_label`, and the labelled assignment uses the hosted app's message with its own `msg_id_seed_label`. The assignment and recurring assignment come from the sealed-value and envelope message inputs. Records that reuse a natural key name its source in `natural_from`. The generation-specific share count appends its policy's named generation. The separate-create-scope record uses the share's natural key unchanged.
- `operations.json` supplies the batch, nonce, attempt and message seeds for the writes after the chain. Operations sharing a new batch name its first operation in `batch_from`. Completion and receipt messages name the messages they reference in `refs` and `body_refs`. Their signed bytes determine the evidence references. Each accepted permanent policy and each `record_scopes` case has its own batch and nonce seeds. A scoped write selects its policy by name and seals `plaintext` under that policy's read scope. Empty plaintext encodes a delete. The guarded write's batch ID repeats `batch_byte` sixteen times. The deny-list peers repeat each chosen byte thirty-two times.
- `encoding.json` supplies one `seed_labels` entry per seeded derive part and a `seed_label` for each seeded base64url example, cut to the example's byte length.
- `sealed.json` supplies a `nonce_seed_label` for each 24-byte nonce and a `msg_id_seed_label` for each message UUID. Its `message`, `record_version` and assignment's `record_status` supply the plaintext inputs.
- `signatures.json` pins the strict verifier's `reason` (null for acceptance) and the non-strict verifier's `lenient_accepts`. All six curve cases use `seed_a` for the scalar. Rejections 4 and 5 use a zero nonce. The other four curve cases derive the nonce from `seed_r`. Rejection 6 uses a fixed non-canonical public key. The other five use `torsion_index`. The counter search starts at zero and emits the first match. Rejections 0 through 2 use the wallet certificate from `documents.json`.
- `documents.json` supplies certificate validity (`issued_at`, `expires_at`) and the renewed `scopes` and `permissions`. App records use `accepts`, `protocols`, `updated_at` and `expires_at`. Identity documents use `signer_seed_label`, `listed_apps`, `policy`, `origin`, `distrust_from`, `version`, `data_epoch`, `until`, `record_max_age` and `generation`. Enrollments use `observed_at`, `store_id_seed_label` and `nonce_seed_label`. The freeze uses `issued_at`, `next_generation` and `nonce_seed_label`. The auth request uses `client_seed_label` and `secret_seed_label`. The approval and its refusal use `keyed_scopes`, `seal_seed_label` and the refused part's `last_epoch`. The document variants select `extra_permission`, `extra_scopes`, a `protocol` and its `member`, or a conflicting record's `board_kind`.
- `envelopes.json` supplies the assignment, cancellation and resend inputs under `messages`, including `kind`, `created_at`, `body` where chosen, and `msg_id_seed_label`. Each resend's `resend_count` and `item_seed_prefix` determine its list of message IDs. Each envelope uses `cek_seed_label`, `nonce_seed_label` and each recipient's `ikm_e_seed_label`. The forged commitment adds `other_cek_seed_label` and takes its two wrap seeds from `ikm_e_seed_labels`. Bundles use `keyed_scopes`, `first_epoch` and `last_epoch`. The two bundles, each refused bundle, each hand-over part and the backup use `seal_seed_label` for their content key, nonce and ephemeral key material. Refused bundles select the added or missing `scope`, or use `key_seed_label` for the conflicting key. The hand-over and backup use the shared `account_created` timestamp and certificates and identities issued in memory. The hand-over, backup and hand-over reader use the enrollment case's `limits` input in `http.json`.
- `chain.json` supplies the batch, attempt, invite code, peer, message UUID, record nonce and fork hash seed labels. The create and update carry the signed messages' chosen fields and the stored record status. The claim attempt's `claim_key` is an input: the service treats it as opaque, and a protocol's apps derive it (spec 10.2). The claim deadline follows the assignment's due time.
- `export.json` supplies a batch seed label on each forged failed entry, both entry ID seeds, and the pending assignment's message UUID and sealing seeds. The two pending entries share an envelope. The admission parts replay the chain's invite and wallet grants.
- `claims.json` supplies the account and app signing seeds, bundle and receive seeds, attempt and evidence labels, and the batch seeds for the published request bodies. A write step names its opaque claim key, attempt, entry fields and optional evidence. Its signed operation carries those fields. The fixture publishes the fields in `op`. A step's `expect_attempts` names, beside the expectation and one entry per attempt in order, the attempt, its owner app and any resolving app of the expected claim view (`claim`) and of a refusal's current claim (`current`). The writer builds the attempt IDs and App IDs of the expected views from them, so each expected view holds only the members an implementation receives.
- `http.json` supplies the saved head's position and hash seed, the request and feed messages and their sealing seeds, the invitation and entry seeds, and the webhook time, handle and nonce seeds. The original peer-list example uses the unversioned identity seed described under Peer admission. The enrollment answer's `limits` member supplies the limits announced on the wire.

Each seed label in the twelve files, including the resend item prefix, determines a generated value besides a description or note.

**Comparisons with published values**

The operations reader verifies signatures, permissions and shapes, checks the embedded certificates, opens the sealed records and verifies the batch rules. The chain reader checks batch hashes in the export. The export reader compares heads and proofs with the chain, signed documents and the transfer with the documents file, and the chunk exchange with HTTP. The documents reader checks the export manifest. The envelope reader compares the limits it opens with the HTTP enrollment case's `limits` input. The HTTP and admission readers compare the pending entries and peer rows in the export with the feed, the peer response and the chain's admission head.

The shared key helper reads seed labels and app parameters from `keys.json`, the claim account and app seeds from `claims.json`, and the pending service and original peer seeds from the HTTP cases that use them. The documents producer also reads the next service's origin and seed there. The sealed-value producer reads certificate validity from `documents.json`, and the envelope producer issues certificates and identities from the document inputs. The export producer reads the transfer's name, signer and issue time from `documents.json`.

The JSON examples in `spec/wire-format.md` are taken from these files, except the `429 quota_exceeded` body of wire 9.3, which is the prototype's answer and says so; update them with the vectors.

The reader clock for each public identity response in `http.json` is its signed `Dispatch-Server-Time`.

After a change to any wire label, including a policy tag, one writer run regenerates all twelve vector files from their inputs. For a seed-prefix change, edit only the Seeds rule above by hand. The writer emits its quote in the `keys.json` description. The core, client and service vector readers take the prefix from that rule. The same writer run regenerates all twelve files with no other hand edits.
