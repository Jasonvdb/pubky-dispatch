# Pubky Switch known issues

Pubky Switch is in development and is not yet safe for real keys or funds. This page describes what protocol authors and host apps can rely on today, where an apparently successful call can give the wrong impression, and which interfaces and stored formats will change. It describes the `main` branch: a change that fixes an item removes it from this page in the same pull request, and a newly found issue is added the same way.

## What will still change

The client's public API for protocols and hosts is in place: record answers that tell an older write from an overtaken one and carry the signed service head, pending duty events with their owners, the delivery outcome `DeliveryUnknown`, permanent record policies, and the certificate-renewal hook `Protocol::member_for`. The signer can recover with the identity key alone, at the account's service or, when that service is gone, refusing or behind, at a service the user picks. The changes still planned add to it; they do not rename or remove what is there.

**Stored formats are not stable yet.** Nothing migrates between development builds: a store, backup or service database written by an earlier build can be refused by a later one. Recreate test stores and databases after updating. The formats still expected to change:

- **Client.** What a kept record job remembers about the delete it follows.
- **Service.** The database and its separate rollback mark now record the count and tag of acknowledged changes at a healthy account. A later mark format will also record a lower bound on the time the service can report.

**Additions still to come**

- **Client.** A protocol will be able to hold the service feed position at a deleted record until its replacement write has applied (a new optional `Protocol` method and two events). `AppEvent::RecordJobStopped` will also name the delete that stopped the job. Public reads used to establish freshness will gain an age check on the signed answer.

**Deferred features.** Cooperative moves between providers and a public generator for the complete test-vector set are deferred. The published vectors are available for checking implementations now.

## Known issues

### Service

- [data] **Recovery enrollment can acknowledge exclusions a restore loses.** A successful enrollment during account creation or while an account needs recovery can leave the rollback mark without evidence of the exclusions it acknowledged. A restore can then lose an App ID the signer expected the service to keep. Preserve the complete database for this account before recovering at the same provider.
- [data] **Takeover can lose the generation recorded before the first chain item.** When the database loses that account, replacing its surviving mark can clear the generation needed for recovery. Keep the service stopped for the affected identity until a database that retains the acknowledged state is available or the signer completes a separately confirmed recovery at another provider.
- [data] **A database restore can repeat a webhook.** The send worker's attempt count and its decision to use a registration are not both covered by the account's rollback mark. Keep outbound push delivery disabled on a restored database until its registrations and pending deliveries are reconciled.
- [data] **Recovery can select the wrong shared record.** An upload without proof from the lost service can displace a proven write, and the first upload at an empty key can determine its collection and policy. Independently reconcile records that authorize an irreversible action before using a recovered value.
- [data] **An embedded service can write without checking that it still holds the instance lock.** The standard executable installs the lock check, but the service constructor allows an embedder to omit it. If you embed the service, connect the instance lock's freshness check before accepting writes.
- [data] **Erasure can report that an account is absent while its data remains.** This happens when an older account is still in storage beside a newer rollback mark that has no chain head. A `not_hosted` response in that state does not confirm erasure.
- [wrong result] **Retiring a forked account can report success for the wrong generation.** When stored account state is a generation ahead of the mark, retirement can leave the recovery notice marked temporary. Check the notice's `permanent` field before telling a user the loss is final.

### Client

- [data] **A deleted record can be forgotten before its repair applies.** A protocol can observe a deletion without holding the service cursor until its replacement write succeeds, including across a restart or restore from an older backup. Keep independent evidence of completed actions when an absent record would otherwise allow the action again.
- [wrong result] **A write conflict can hide a rollback.** The client does not judge the view and head in a `409` answer for an older write, so a service showing an older version there raises no alarm. Treat a conflict that repeats against a version older than the one you hold as a possible rollback.
- [wrong result] **A refused write the app follows is not compared with later ones.** After a protocol refuses a record's first write, a later answer showing an older write is not checked against it. Keep the protocol's own evidence of the refused version.
- [data] **A record job can write over a different deletion at the same version.** After a recovery, two deletions can share a version, and an automatic retry of a record job can apply over the one its protocol never saw. Re-read a record after a recovery before relying on a job that was queued before it.
- [availability] **A record can stay unwritable after a refused first read with nothing held.** When a first read is refused because the record fails a check (not the protocol's own rule), the next write is a create that keeps conflicting. Read the record again after fixing its content elsewhere.
- [wrong result] **A restored backup can deliver a message the app already gave up on.** A backup taken before a message was withdrawn still holds it for delivery. Restoring that backup onto another store, after the protocol was told `MessageUndelivered` and acknowledged it, can deliver the original. Keep the original message ID, and do not issue a replacement the recipient would act on twice while an older backup can still be restored.
- [data] **A device clock change can reopen a batch's retry window.** After a long suspension, a clock set back close to its earlier value can make an old service-time sample look recent, allowing a retry after the service forgot the batch ID. Reconcile the original effect before repeating work that could apply twice.
- [data] **A restore can lose unfinished provider-loss work and list history.** App backups omit the recovery progress, contacts and deny-list copies, and replace an outstanding unchecked deny change with a fresh list read. A protocol can miss its recovery callback or the individual change, and a restored app with list-management permission can finish admission recovery with empty contacts.
- [data] **A waiting message can disappear between feed pages.** The client detects a different item at a position for which it kept an observation, but a later page can omit that position entirely. A cursor past the position is insufficient evidence that the protocol received the message.
- [data] **One stalled protocol can cost another messages.** A shared deny-list change or missing list baseline can stop the whole app's feed until every protocol catches up. Monitor stalled callbacks and listings because other protocols can miss entries if the app falls behind retention or fills its inbox.
- [data] **Senders share the limit on messages waiting locally.** At the total limit, traffic from two admitted senders can cause another sender's waiting entries to be discarded. Consume the durable drop notices and request the missing messages again where the protocol permits it.
- [data] **Some discarded work cannot be identified after restart.** A stored message outside the bounded waiting pool can fail a check on retry and disappear with only an in-memory event, while an in-place restore can reduce some unreadable pending duties to a count. An empty queue cannot establish that every obligation completed.
- [keys] **An old public directory answer can still authorize action.** A previously valid answer can count as a current peer lookup or establish an obsolete service key on a client without a pin. Require fresh independent evidence before using a public lookup to change trust or authorize an irreversible action.
- [wrong result] **A recovery notice does not reliably suspend saved writes.** The client can retry a saved batch after `recovery_required`, and a signed `not_hosted` response can surface only as a call error while the identity document still names that service. Pause submissions and confirm the current service and generation before resuming.
- [wrong result] **A restore can be declared clean using confirmation of a different identity version.** The cursor check uses the time of confirmation even if the app has since taken a newer identity document. Confirm that exact document before resuming automatic actions.
- [wrong result] **A newly held peer can still gain inbox admission.** If a batch adding its conversation was already sent and the answer was lost, the client can retry that batch after the host places the hold. Treat admission as unresolved until the earlier write is reconciled.
- [availability] **Two successive provider losses can leave a record readable but unwritable.** The client can retain the original proven version while the latest service reconstructs a lower version for the same write. Retrying the same conditional update keeps failing, and treating the record as absent risks repeating its effect.
- [availability] **An incorrect service clock can make an app's records unusable.** A far-future signed time can become the minimum timestamp for later app records, including after the device clock moves backward. Other apps can reject every such record as too far in the future even after the service clock is corrected.
- [data] **Two devices of one app can overwrite each other's protocol member.** When both change the same member, the later record wins and the earlier change is not merged. The protocol on the device that lost is told with `MemberChanged`; write the member again there if it still applies. A member taken from another device's record also arrives without that device's expiry request, so the next plain renewal signs it with no deadline; the protocol is told with `MemberChanged` and can set the expiry again.
- [availability] **One protocol's expiry can block app-record signing for all protocols.** A fixed expiry request can block app-record signing for every protocol once its deadline passes, also when its protocol has no member in the record. At a certificate renewal such a request is dropped and reported with `MemberDropped`, but ordinary signing still refuses. Clear or renew the request before its deadline.
- [availability] **Larger valid lists and backups can exceed one local commit.** The client installs a list copy or restores a backup in a single transaction, so raised service limits can permit data the app cannot refresh or restore. Exercise both operations at the largest sizes the host intends to support.
- [availability] **Changing the set of protocols can prevent load or restore.** A normal load requires the registered set to match, adding a protocol requires a restore, and removing one can make backups containing its state unusable. Keep the old protocol available while its backup layer or expiry policy is still needed.
- [wrong result] **A duplicate can be reported as conflicting before the sender's authority is checked.** This can happen when a previously stored copy is released and its bytes differ from the processed copy. The conflict flag alone is insufficient grounds to accuse or block the sender.
- [wrong result] **Requeuing a signed message can report the wrong kind of error.** `queue_stored` can report caller misuse when today's message rules reject previously valid bytes, or store corruption when different bytes reuse a retained message ID. Check the rules, ID and original bytes before taking action on the store.
- [wrong result] **A protocol wait can look like a storage outage.** The general retry outcome takes a storage failure, so using it while waiting for a record or list can produce `StoreFailing` on repeated reads. Check the protocol's reason before treating that event as evidence of damaged storage.
- [wrong result] **The recovery count can overstate how many peers were left out.** A peer beyond the conversation limit can be counted once for each protocol that named it. Display `conversations_left_out` as an upper bound on distinct peers.
- [wrong result] **A custom request can reach a different target from the one signed.** The low-level transport accepts methods outside the Switch wire format, some of which encode the request target differently. Hosts constructing requests directly should use only the methods defined for the endpoint.

### Signer

- [keys] **A hand-over can strand the only sealed copy of the identity key.** The receiving device installs the key in its vault only after the service confirms that the device has taken over. Retain an independent copy of the key until the receiving vault has confirmed possession.
- [keys] **An accepted permission reduction can leave the previous certificate effective.** If the signer cannot obtain the service time needed to close the reduction, the earlier certificate can retain its wider permissions. Surface `ReductionNotClosed` and use revocation when access must end immediately.
- [keys] **Some damaged signer stores cannot be restored in place.** Certain invalid stored values fall outside the damage the restore call accepts, and a surviving operation or alarm can also block replacement. Preserve the store and the identity key because discarding the records can discard restrictions on who may sign.
- [availability] **First enrollment can become impossible to finish in place.** If its account observation expires or the service permanently refuses the creation request, `resume` keeps the original signed request and the signer stays `Enrolling`. Repeating setup on the same store cannot obtain a new enrollment.
- [availability] **Key recovery can reject the confirmation it just requested.** With damaged records, execution can omit verified local evidence used to prepare the confirmation, and changing genuine answers between reads can repeatedly produce `SurveyChanged`. Reconfirmation may never finish even when the user still has the key. Declaring a provider loss with the key acts on the survey the user confirmed and refuses only what is new, so a source that merely shows less no longer blocks it; a source that shows something new on every read still does, until a read at another time gets past it.
- [availability] **An interrupted key recovery has no ordinary cancel operation.** Persistent storage or communication errors can leave recovery pending and block other signing operations on that installation. Preserve the pending state so recovery can resume when the dependency is available.
- [availability] **Repeated recoveries can consume the space needed to approve apps.** Revoked app IDs reported by the service are bounded per recovery but retained across recoveries. An identity can eventually refuse a legitimate approval because its signed document no longer fits.
- [data] **Key recovery at a lost service can drop revoked App IDs without saying how many.** When more revoked IDs exist than one enrollment carries, the extra ones that no version of the identity document lists are dropped, and the survey does not show the count. A dropped ID comes back only through a new approval by the user.
- [data] **A temporary rate limit can cause recovery to skip usable backup data.** If the backup's service returns `429` during its check, key recovery can proceed without the backup's key-bundle parts and with limits taken from enrollment. Retry after the rate limit clears before relying on the reconstructed state.

### Specification

- [keys] **Changing a service key does not retire its authority for every account.** The specification leaves the signer notification and authenticated link between successive keys undefined, so clients can continue trusting a compromised old key while their identity documents name it. Replacing the operator's key alone is insufficient to secure those accounts.
- [specification] **The service-time guarantee is stronger than the stored evidence.** The specification says an account's time never goes backward, but a failover can restore an earlier database timestamp while the separate rollback mark still matches. Do not use two service timestamps alone to establish the order of actions across failover.
- [specification] **`ProviderStatus::Current` can be reported for a frozen account.** The wire rules require a signed request to establish the absence of a freeze, but `check_for_move` can return `Current` after a public read that shows none. Use a response to a signed account request before telling the user that the account can accept writes.
- [specification] **Enrollment reports only some effective service limits.** Clients receive limits such as batch size and storage quota, but must assume defaults for others, including contact and conversation counts. Handle limit refusals even when a request fits the published default.

## Not yet covered by tests or measurements

Some checks for write-lock ownership, recovery evidence and pending work still lack a test that fails when the individual check is removed. Large recovery transactions, slow connections and outbox operations that repeatedly scan and verify retained messages need measurements at realistic sizes. Cleanup remains in duplicated decision logic, test fixtures and host guidance.
